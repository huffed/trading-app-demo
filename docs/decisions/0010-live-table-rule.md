# 0010 — The live-table rule and the broker exception: three targets write the live tables, one may flatten the broker, and no committed make rule can pre-approve them

**Date** 2026-11-01, the broker half 2026-11-02, corrected 2026-11-06, the MetaApi redeploy 2026-11-06 · **Status** active, amends 0008 · **Decided by** the operator (wording), with the enforcement added after the review of PR #317

## Decision

`CLAUDE.md`'s last rule said nothing that writes to the live tables runs from a Claude session. `make kill-switch`, `make resume` and `make unpause` do, by design (0008). The operator amended the rule rather than denying the targets: **no session writes to the live tables except through those three, each of which prompts every time, is never pre-approved, and writes a ledger row.** The three targets' help text, the runbook and `docs/DEV_SETUP.md` §18 carry the same wording; like every host command, they run only when the operator asks. The broker half, 2026-11-02: **no session acts on a broker account except `make kill-switch`, which may flatten mirrored positions.** The flatten is the one session path that closes a broker position itself, and that is its purpose — a kill switch that cannot flatten the broker is not one. Scope, same day, corrected 2026-11-06: "acts on a broker account" means placing, modifying or closing orders, or changing account settings; read-only broker access from a session is allowed. Once mirroring is on, `make resume` and `make unpause` count as acting on the account, because together they let the engine trade again: they prompt, print the mirroring state and write a ledger row, as `make kill-switch` does.

## Why

Denying the targets would have left the emergency stop runnable only by hand from a terminal. The operator wants it one prompted command away from any session, with the record it already writes.

## Alternatives considered

- `deny` rules for the three targets — rejected by the operator.
- Wording alone — rejected by the fresh-context review of PR #317: `make lint-strict FILES=x unpause` matched the pre-approved `make lint-strict *` rule, matched no `ask` rule, passed the Bash guard, and would have run the un-pause with no prompt. make runs every goal on its command line. The claim needed enforcement.

## Consequences

- Makefile: a host goal (`deploy deploy-pointer status logs kill-switch resume unpause`) beside any other goal, or a `MAKECMDGOALS` that make did not set itself (`$(origin MAKECMDGOALS)` is `default` only when make set it; checked on GNU make 3.81 locally and on CI's make by the dry-run tests), is refused with `$(error …)` while make reads the file — nothing runs. `.DEFAULT_GOAL` is `override`, so a command-line `.DEFAULT_GOAL=unpause` cannot make a host target the default goal. This check covers goals only: it never sees a prerequisite injected by `--eval`, which is why the first layer below is the real backstop.
- No pre-approved make rule takes arguments, so every make command with arguments prompts, whatever its spelling: `Bash(make lint-strict)`, `Bash(make format-check)` and `Bash(make regime-report)` are exact (each target has a default — `lint-strict` lints the files added vs `BASE`, as CI does; a form with arguments prompts), and the skills' `allowed-tools` are exact too. A wildcard rule such as `Bash(make lint-strict *)` would have pre-approved `make lint-strict FILES=x '--eval=lint-strict: unpause'`, which runs the un-pause as a prerequisite before any goal check (the review's verification pass found it).
- `.claude/hooks/guard-bash.sh` refuses, before the command reaches make: a host goal beside another goal, behind a flag (`make -s unpause`) or behind an override (`make REASON=x kill-switch`) — quotes around a single word are seen through, a quoted span with spaces counts as one token; the `-f`, `-C`, `--eval`, `MAKEFILES=`, `MAKEFLAGS=` and stdin-makefile spellings it can see through (quotes, backslashes, env prefixes) — a text classifier (DEBT D-22), not the backstop. `.claude/settings.json` asks for every flagged `make -…`.
- `tests/ops/makefile-host-targets.test.ts` fails if an allow rule in `.claude/settings.json` (or in `.claude/settings.local.json` on a local run — that file is gitignored, so CI never sees it) could pre-approve a host target: a blanket `Bash` or `make` rule, a flag form, a host target anywhere in the rule, or a wildcard prefix that could grow into one; if any `Bash(make …)` allow rule — committed, in a skill's `allowed-tools`, or local — takes arguments; if either spelling of the three targets, or `Bash(make -*)`, leaves the `ask` list; or if make accepts a host goal beside another.
- Not covered: user-level settings, `--allowedTools`, a pre-approved program that runs make or code for you (`pnpm exec vitest run *` and `prettier --check *` are in the committed allow list). The operator removed five pre-approvals and an env-file read from `.claude/settings.local.json` on 2026-11-01, and `Bash(pnpm dlx:*)`, `Bash(npm run:*)`, `Bash(pnpm run:*)` and the prefixed `pnpm dlx` entries on 2026-11-02 (a pre-approved program could otherwise have run make).
- Covered by Claude Code's matcher, not by a layer here: a leading `VAR=value` prefix. A default-mode session prompted on `FOO=1 make help` (operator, 2026-11-02; the workstation had Claude Code 2.1.308 installed, the test session's version was not recorded), so a prefix does not bypass an exact rule and the `FILES=`, `BASE=` and `PNPM=` variables that `make lint-strict` expands need no further treatment. The test covered an exact rule; a wildcard rule such as `Bash(git status *)` was not tested, so `FOO=1 git status` is part of the re-run procedure in `docs/DEV_SETUP.md` §16.
- "Ledger row" in `CLAUDE.md` is the operator's word for the pair: the line the script appends to the host's `deploys.log` and the row copied from it into `docs/decisions/deploys.md` in the next PR. A failed append counts as an error in all three scripts, and an un-pause whose PATCH failed writes `UNPAUSE result=unknown`, because it may have committed (DEBT D-24).
- The broker half was open until 2026-11-02 and is decided above: `CLAUDE.md` names the kill switch as the session path that closes broker positions itself; once mirroring is on, resume and un-pause also count (scope above). What the flatten does (`src/lib/scan/flatten.ts`, `/api/admin/flatten-algo`): it closes the broker side of each still-open paper position that carries a `broker_position_id`, on the algorithms the switch pauses, through that algorithm's current broker connection; it ignores `live_trading_enabled` and a connection's `disabled` status. It does not reach a broker position whose paper row is already closed (a failed exit close, `live-execution.ts`), or whose algorithm was paused before the switch ran (the alpha-decay auto-pause pauses without flattening), which the switch reports as `open-untargeted:N` and does not flatten. Mirroring off opens no new broker positions but does not rule out old ones (audit F13).
- The switch reports a broker position that did not close as an error, and later runs repeat it until `make unpause`, but the paper row still closes whatever the broker answered, so a re-run cannot retry it (DEBT D-25: the fenced half waits for the audit verdict). A re-run after `make resume` flattens every id the engagement targeted (D-27). D-26 records that orphan adoption can adopt a position the engine did not open. D-25 and D-26 are dormant while mirroring is off.
- All three scripts print the mirroring state: `live_trading_enabled` as `on/total` for the algorithms the switch targets, and for the saved ids in `resume.sh` and `unpause.sh`. It is on each ledger line as `mirroring=`, including `UNPAUSE result=unknown`. It reads `?` when the read fails and `n/a` when there is no id list to read; neither is an error. That the kill switch prints it too is this decision's reading of the operator's "same as make kill-switch".
- The printed mirroring state is a record, not a safeguard (operator, 2026-11-06). The permission prompt shows only the make command and the script cannot stop for an answer, so the state appears during or after the action it describes. To see it before approving, read `algorithms.live_trading_enabled` first.
- A MetaApi redeploy is not an act on the broker account (operator, 2026-11-06). `REDEPLOY=1` on `scripts/canonical/metaapi-connection-doctor.ts` restarts MetaApi's cloud terminal, not the account, so it is infrastructure, like a service restart. It prompts every time, is never pre-approved, and gets a ledger row. While mirroring is on it runs only through a written incident runbook, because the restart drops the connection that manages open positions. No such runbook exists yet, so today it does not run with mirroring on. The `ask` rule in `.claude/settings.json` covers every run of that script, including the read-only diagnosis, and `tests/ops/makefile-host-targets.test.ts` pins it.
- Read-only broker access is allowed, but no routine session command needs it today: `make status` reads local host state, `make parity` is a stub, and the audit's `paper-replay.ts` reads the database and pinned files. Five scripts in `scripts/canonical/` read a broker. `capture-broker-spread.ts` and `sample-forex-spreads.ts` write local files only. `sync-account-capital.ts` writes `broker_connections.account_capital` with `APPLY=1`. `snapshot-broker-health.ts`, which the host's `broker-health` cron runs every six hours, writes `broker_connections` unless `APPLY=0`, so it is not read-only by default. `metaapi-connection-doctor.ts` writes `broker_connections` with `APPLY=1`, and with `REDEPLOY=1` it POSTs a redeploy to MetaApi, which is not read-only access.

## Evidence

Review of PR #317 (2026-11-01): the multi-goal bypass, the test's misses (`Bash(make -s *)`, `Bash(make REASON=x kill-switch)`, `Bash(make k*)`), the two ledger-line gaps, the dropped "only when the operator asks". `tests/ops/makefile-host-targets.test.ts` and `tests/hooks/cases.ts` pin the fixes.
