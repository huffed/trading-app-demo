# 0013 — Working with the operator: blocks visible on the phone, questions at the end, merges by the operator

**Date:** 2026-11-13 · **Status:** active; the operator adopted the pushes and the docs rule on 2026-11-17 and rewrote the review loop for code, tooling and runbooks; two rules added that evening (repeated questions, DEBT-rows conflicts) · **Number:** 0012 is the live-table statement decision the operator queued on 2026-11-07 and made on 2026-11-17.

## Decision

- **Waits reach the phone.** One hook script pushes to the operator's ntfy topic, with the access token if the topic is reserved (`docs/DEV_SETUP.md` §16). On Notification it pushes permission prompts, idle waits and requests for input. On Stop it pushes a turn whose text has the **BLOCKED ON YOU** line with numbered questions under it, read from the turn's last text and, failing that, from its earlier text in the transcript, at once and once per set of numbered lines, because Claude Code holds the idle push back while a background agent runs; a BLOCKED ON YOU line it cannot read is said in the log and in a hook message for the operator, which the session never sees (D-44). The three types the operator named send Claude Code's message, a dialog sends fixed text, and the Stop push sends the number of questions, never their text; every push also carries the session name, cut to 60 characters. Sessions start with `caffeinate -is claude`.
- **Questions only at the end of a turn,** under a line that reads **BLOCKED ON YOU**, one per numbered line, each with a recommended answer; what the session carries on with meanwhile is said above them and started before them, so they are the turn's last text. Later turns repeat them while they are open. A turn ends with READY TO MERGE, then BLOCKED ON YOU, each only when it has items, then, when the session's work is outstanding, a `Next action:` line that names the next action and who starts it.
- **Order.** The operator's queue order stands; the session's own findings go to the end as proposals. A claim about how a tool behaves says what was run to check it.
- **Merges.** The session no longer merges on its own. A review-clean, green PR goes on the **READY TO MERGE** list, and the operator says "merge the queue". The session then merges each listed PR in order. Because `protect-dev` requires an up-to-date branch, each merge is `gh pr merge <n> --squash --match-head-commit <sha>`, and a PR behind `dev` is first rebased with `gh pr update-branch <n> --rebase` and merged once CI is green at the new head; a PR whose rebase conflicts leaves the list until it is resolved and reviewed again, unless the conflict is confined to `docs/DEBT.md` rows with both sides' rows kept whole, which needs no review and which the PR says so (operator, 2026-11-17, evening). This replaces "then merge it yourself" (operator, 2026-10-30).
- **Review rounds.** Reviews label every finding Critical, High, Medium or Low. A docs PR with no runnable command gets one review round. It is clean when that review reports no Critical or High, and Medium and Low findings are fixed in the same push; a Critical or High is fixed and gets one more review under the same rule. Code, tooling, runbooks and plans with host commands get at most three rounds: the first reads the whole PR, each later one only the diff since the last reviewed commit, and confirms the earlier findings are closed. The loop ends at a review with no Critical or High. A Medium is fixed in that push when a single failure reaches it or it is inside the PR's stated scope, and otherwise goes to `docs/DEBT.md` with the PR number; a Low is fixed when the fix is one line, and otherwise goes to `docs/DEBT.md`. If round 3 still has a Critical or High, the session stops and brings the finding to the operator with the options: cut scope, ship with it recorded, or redesign. Once a PR is review-clean, a rebase that needed a conflict resolved, or a later edit, gets one review of that diff only; the merge queue's `gh pr update-branch --rebase` needs green CI only (Merges); unless the conflict is confined to `docs/DEBT.md` rows with both sides' rows kept whole, which needs no review and which the PR says so.
- **The hook is frozen.** It gains no behaviour unless the operator asks (2026-11-17).

While questions are open, every later turn repeats the numbered lines word for word. A question already asked is repeated as its number and first line only, that line word for word, so an unchanged set is not pushed again (operator, 2026-11-17, evening). The phone gets each set once.
- **A turn ends in this order:** READY TO MERGE, then BLOCKED ON YOU, each only when it has items, then, when the session's own work is outstanding, a last line that starts `Next action:` and names the next action and who starts it.
- **The operator's queue order stands.** The session's own findings go to the end of the queue as proposals.
- **Every claim about how a tool behaves says what was run to check it.**
- **Merges.** The session does not run `gh pr merge` on its own. A PR that is review-clean and green goes on the **READY TO MERGE** list at the end of the turn, with its number and head commit, and the session moves on to the next independent item. When the operator says "merge the queue", the session merges each listed PR in order with `gh pr merge <n> --squash --match-head-commit <sha>`, where `<sha>` is the listed head, once it is still green there. A PR that is behind `dev` (`protect-dev` requires an up-to-date branch) is first rebased with `gh pr update-branch <n> --rebase`, and merged with the new head's sha once CI is green there. A PR whose rebase conflicts leaves the list until the conflict is resolved and the PR is reviewed again, unless the conflict is confined to `docs/DEBT.md` rows with both sides' rows kept whole, which needs no review and which the PR says so (Review rounds).

  - A docs PR with no runnable command (DEBT rows, decisions, ledger text) gets one fresh review of the whole PR. It is review-clean when that review reports no Critical or High; Medium and Low findings are fixed in the same push, with no further round. A Critical or High is fixed, with the Medium and Low, and the PR gets one more fresh review under the same rule.
  - Code, tooling, runbooks and plans with host commands: round 1 reads the whole PR; each later round reads only the diff since the last reviewed commit and confirms the earlier findings are closed. The loop ends at a review with no Critical or High. A Medium is fixed in that push when a single failure reaches it or it is inside the PR's stated scope, and otherwise goes to `docs/DEBT.md` with the PR number; a Low is fixed when the fix is one line, and otherwise goes to `docs/DEBT.md`. Three rounds at most: if round 3 still has a Critical or High, the session stops and brings the finding to the operator with the options: cut scope, ship with it recorded, or redesign.
  - Once a PR is review-clean, a rebase that needed a conflict resolved, or a later edit, gets one review of that diff only; the merge queue's `gh pr update-branch --rebase` needs green CI only (Merges). A rebase conflict confined to `docs/DEBT.md` rows, where both sides' rows are kept whole, needs no review; the PR says so (operator, 2026-11-17, evening).
- **Being visible.** The operator starts sessions with `caffeinate -is claude`. Two pushes reach the operator's phone (`docs/DEV_SETUP.md` §16), from one hook that gains no behaviour unless the operator asks (2026-11-17):
  - the Notification hook's, for a permission prompt left about 6 s, an idle wait of about 60 s, a question from a background session, and a dialog; Claude Code holds the idle one back while a background agent runs;
  - the Stop hook's, at once, for a turn whose text has the BLOCKED ON YOU line with numbered questions under it, also while background agents run.
  - A push that does not go out is logged in `~/.local/state/quanttrader/notify.log`; on Stop it also leaves a hook message for the operator, as does a BLOCKED ON YOU line the hook cannot read (the transcript records it; its display on screen is not yet confirmed). The session does not look into a failed push, and no session reads `~/.config/quanttrader/` (a `Read` deny covers the file tools and the Bash file commands Claude Code recognizes, not every read: D-42); the hook's message never reaches the session (D-44), so when the operator says a BLOCKED ON YOU section could not be read, the session writes it again in the form above. `gh pr merge` prompts (an `ask` rule; D-43).

## Why

The session's retrospective of Parts A and B (2026-11-12; a private document outside this repo) counted 179.5 of 364.7 tracked hours as waiting on the operator. Part of that wait the operator could not see:
- permission prompts left open for 46.2 h (stalls S1 and S3–S7);
- questions inside long reports;
- a fix promised at a hand-off that waited 75 h with nothing scheduled (E32).

Docs-only PRs took 20 review rounds, and their first reviews found no Critical and six Highs, all of them wording.

The review loop for code and tooling as first proposed here ended only at a whole-PR review with no Medium. The operator rewrote it on 2026-11-17: "#336 took 6 rounds, #342 is past 8, and #338 is 13 commits and 1,100 lines for a push hook. A fresh whole-PR review always finds another Medium, so 'no Medium' never ends."

## Alternatives considered

- **A `systemMessage` from the hook when a push fails, so the session shows it:** not possible. The hooks reference says a Notification hook's `systemMessage` is discarded, and its exit code ignored.
- **A push from the Stop hook at every turn end:** rejected; most turns need nothing. The Stop hook pushes only a turn with the BLOCKED ON YOU line.
- **The session reading the hook's log before a BLOCKED ON YOU turn ends** (this PR's first fix): replaced. A turn's idle push fires after the turn, so the read saw an earlier push, and the idle push never comes while a background agent runs (review of 2026-11-13).
- **The session merging after review, the old rule:** rejected by the operator.
- **A code and tooling loop that ends only at a whole-PR review with no Medium** (this PR's proposal): replaced by the operator's rule above, on 2026-11-17.
- **The session name from the status-line input, where Claude Code documents it:** hooks do not receive it, so the hook reads the transcript's title records and falls back to the folder name.

## Consequences

- A sleeping Mac sends nothing.
  - `caffeinate -s` holds only on AC power.
  - On battery the Mac still sleeps: all 349 sleeps since 6 November in `pmset -g log` were on battery, with a `caffeinate -dis` running; the log does not show why.
- A prompt answered within about 6 s sends nothing, by Claude Code's design. The idle push waits for background agents; the Stop push does not.
- A turn that ends with questions and no background agent running sends two pushes: the Stop push at once and the idle push about 60 s later (`notify.log`, read 2026-11-16: each of the thirteen idle waits came 62 to 66 s after a Stop line).
- Questions reach the phone only when the turn ends, so meanwhile work in the foreground holds them back; a session with questions puts longer work in background agents.
- Nothing is sent until the topic file exists. A reserved topic also needs the token file, and without it ntfy refuses the push; the log line then names the token file.
- The session name depends on Claude Code's internal transcript format.
- `docs/DEBT.md` D-42 to D-45: a `Read` deny on `~/.config/quanttrader/**` may not stop a pre-approved `git diff --no-index`, and does not stop a script, printing the secret files; a merge spelled other than `gh pr merge` is not covered by the `ask` rule, so in auto mode the classifier decides; a failed Notification push is only logged; the session name and the earlier-text fallback read Claude Code's internal transcript format.
- The `ask` and `deny` rules and the hook reach a session only from the checkout it was started in.
- The hook needs jq; without it nothing is sent, and on Stop it says so.
