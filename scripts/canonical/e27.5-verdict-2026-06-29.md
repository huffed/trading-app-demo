## What broke: structural DD floor at gold 4h

Looking at the per-pattern augmented metrics, the failure is concentrated on **criterion 3: max_static_dd ≤ 10%**. Of 120 (pattern × feature) combinations tested across both cells, the augmented variants distribute roughly:
- ~30 combos: trade count drops to 0-20 (criterion 2 fails immediately — augmentation over-constrained the entry)
- ~70 combos: trade count adequate (≥30) but DD lands in 11-25% range (criterion 3 fails)
- ~20 combos: trade count adequate AND DD ≤ 10% (could be passers by 2+3) but FAIL on other criteria (Sharpe, mean_r CI, OOS) — none pass all 7

**Why DD ≥ 10% is structural:** XAU/USD 4h volatility per the 10.5-year H.0 cache produces peak-to-trough equity drawdowns that don't respond to entry-signal modification. Augmentation reduces the trade rate but doesn't reduce per-trade RISK (which is set by stop-loss geometry × position-sizing). The DD floor is determined by gold's volatility regime + the candidates' geometry, not by entry selection.

**Why the SURVIVORS DO pass per-candidate:** the survivors (Engulfing + ARB) have lucky alignment between their pattern signal + the gold 4h volatility regime such that their specific entry timing happens to clip the worst DD periods. Non-survivor patterns + augmentation can't replicate this alignment without modifying geometry (which is what E2.7 cluster-stability proved can't be improved further at this data depth).

## Critical bug fixed during this run (in `augmented-variant-validate.ts`)

**Severity: HIGH** — affected all prior augmented-variant-validate runs that produced PASS verdicts on DD criterion when actual DD > 10%.

**Bug:** `augmented-variant-validate.ts` line 132-133 computed `max_static_dd_pct = (peakDdDollars / capital) * 100` where `peakDdDollars` was misnamed — it actually contained the percentage already (from `propReport.peak_drawdown` which is `peakDrawdownPct.toFixed(2)` per `prop-firm-backtest.ts` line 608). Double-conversion produced values 100× too small (e.g., 13.19% DD → 0.1319 stored). Per-candidate gate via criteria.ts then compared 0.1319 ≤ 10 → PASS (spuriously).

**Fix (this commit):** removed the second `/ capital * 100`; renamed variables to `peakDdPct` / `dailyLossPct` for clarity. Now reads the percentage directly from propReport.

**Prior runs affected:**
- v3 survivor + daily_bias augmentation (per-candidate PASS verdict): actual DD was 6.65% which passes either way; verdict stands.
- 7-veto feature-veto runs (per H.4-methodology-revision): need re-audit; most augmented variants had DD ≤ 10% per recorded metrics so unlikely to flip, but recommended re-run.
- Any H.4b prior result claiming per_candidate_passes=true with `max_static_dd_pct` between 0.10 and 0.30 → likely false positive; needs re-verification.

Filed as ROADMAP punch item CB.X6 (codebase audit; small, scoped re-verification work).
